# Features beyond the template

Everything below exists in `exam1-drill/src/` as of 2026-10-17. Each item names the file and the function or data it lives in, so another course can find and adapt it. Items marked **content-bound** carry course material and are rebuilt per course; the rest is engine.

## What the student sees

### Exams as collapsible groups, one site for the whole course
- `course.js` carries `exams[]` with `id, name, scope, date, when, questions, minutes, blurb, pools[]` and `activeExam`; every lecture carries `exam` and `module`.
- Topics, Guides, Reference, Tell apart, Terms and Readings draw one `<details class="exgroup">` per exam (`exGroup()` in `app.js`), the exam being studied open, the others folded. The exam switch (`examSwitch()`) is on Topics, Exam sim, Weak spots and Terms.
- Per-exam pages: `guide<N>.js`, `reference<N>.js`, `tell<N>.js` for each exam; `PAGE_BY_EXAM` in `app.js` maps exam id to the three page strings, and `examPage()` renders the groups. Adding Exam 4 is three page files and one map entry.
- Professor tag: a Topics card shows "<Name>'s lecture" when the lecture's `prof` is not the first listed professor (`topicCard()`), for a course taught by two people.
- The exam blurb states what is in the bank so far (`exams[].blurb`); the "What's new" card (`newsCard()`, `CHANGELOG.md`) lists the latest additions.

### Links from every question to its explanation pages
- `linksFor0(q)` returns `[view, anchor, label]` triples per question: keyword rules for Exam 1 (`LINKS`), keyword rules then lecture fallbacks for Exam 2 (`LINKS2`, `BY_LECTURE2`, `TERM_SUB2`), a sub map for the first Exam 3 lecture (`SUB3`) and a `"<lecture>:<sub>"` map for later lectures (`LINKS3`, `BY_LECTURE3`). The "Explain more" chips after an answer use these; "Back to the question" restores the question and scroll position.
- `test.js` can check that every anchor exists in the page strings (added for readings; extend to `LINKS3` when porting).

### Readings page (new 2026-10-17)
- `readings.js` is generated by `gen_readings.py` from `src/readings/*.json` (one card per assigned reading) plus a `META` table in the generator (exam, lecture ids, status, Drive file id, links to guide and reference anchors).
- `vReadings()` renders one card per reading grouped by exam: title, status chip (discussed in class, behind the professor's slides, assigned, upcoming, his chapter), source and lecture line with an Open in Drive link, a two-sentence summary (`rdLead()`), a Drill button over the questions tagged with `readingId`, a button for the professor's quiz items on that reading, chips to the related sections; folds for About in full, Read for, Where the lecture used it (verbatim quotes with dates), the professor's words, Terms it defines, Beyond the lecture.
- Questions link to a reading through `readingId:"<card id>"`; `test.js` checks ids, anchors and references.
- Card JSON schema: `id, title, source, file, lecture, kind, about, sections[], lecture_use[{point, chapter_location, lecture_evidence, date}], read_for[], beyond_lecture[], terms[{term, chapter_definition}], discussed_in_class, her_words|his_words[{t, date}], truncated, numbering_note, listen`.

### Listen deck (new 2026-10-17)
- On the Readings page: Play all, Shuffle, Next, Stop, speed; one two-to-three-minute talk per reading, in order or shuffled; tapping a title starts there; the talk's text shows while it plays; leaving the page stops it (`rdPlayFrom`, `rdPlayCur`, `rdNext`, `rdStop`, hooked into `leaveView()`).
- Clips are expected at `audio/rd-<id>.mp3`; if a clip cannot be loaded the device voice reads the script (same fallback as the figure narration). Scripts live in each card's `listen` field; `notes/READINGS_LISTEN_SCRIPTS.md` lays them out for approval before generation.

### Narration (recorded, with a device-voice fallback)
- Figure steppers narrate each step (`narration.js` `NARRATION[key][i]`, clips `audio/<key>-<i>.mp3`); "Hear the why" on a question reads the recorded explanation (`NARR_Q[id]`, clips `audio/q-<id>.mp3`); the Scenes page plays animated process scenes with synchronized narration (`scenes.js`, `vScenes()`); the drug list has a narrated walkthrough (`dlListen()`).
- `NAR` holds mode, rate and voice; `NAR_BASE()` resolves the audio folder for the repo root `index.html` and the folder copy; `speakable()` rewrites written forms the voice would misread. `test.js` checks scene scripts for length and for forms the voice must not read.
- Clips were generated with ElevenLabs (voice and model recorded in the session notes), one take per clip, cost reported before generation; the site works with sound off.

### Drug ↔ receptor drill (content-bound to a drug table)
- `vRxq()` and the `RX_*` helpers: name the receptor and action for each drug on the course table from five written answers, or name the drug from a receptor, action and site; misses return at the end of the round; best score per mode is kept. Built on the drug rows in `drugs.js`; a pharmacokinetics course would replace it with a parameter or equation drill of the same shape.

### Pair up, Scenes, Diagrams, Graphs, All drugs, Question map, Weak spots, Exam sim, Progress
- Carried over from the Exam 2 work; see `notes/ENGINE_UPGRADES.md` for the engine notes on Weak spots (concept-level remediation, spaced review, stable id aliases), steppers (FLIP motion, reduced motion), the Diagrams tab, explain-one cards, Terms search, and the blueprint draw.

### Verbatim polls and quizzes in the bank
- The professor's Poll Everywhere items, practice quizzes and Jeopardy items are in the bank word for word under `sub:"verbatim"` with the tag `pollev` or `quiz`; `test.js` and `style_check.js` exempt those from the longest-option and option-wording rules. A short-answer quiz item is kept as multiple choice with a note that it was free response.

## How content is produced

### Source hierarchy and keying
- The transcript keys every answer; the slide is second; the reading third, and only as discussed in class. A slide the professor did not reach gets `lowYield:true` and a note; when the next lecture covers it, the question gets the quote, loses `lowYield`, and its cite adds the transcript date.
- Decks with no printed slide numbers are cited by slide title in quotation marks; `course.js` lectures carry `decks:[...]` when a lecture spans more than one file, and `test.js` accepts any of them in a cite.
- Every `quote` is an exact transcript substring (transcription errors kept); the verifier tests this by script.
- Conflicts between what was said and what the slide prints are recorded in `note` and in `notes/L<N>.md`; the bank keys what was said.

### The professor corpus
- `STYLE.md` holds, per lecture day: every poll verbatim with the professor's verdict per option, every question put to the room with the accepted answer, every sentence about the exam or the quizzes, and what was deferred. The guide's scope section quotes the professor's own description of difficulty (polls below quizzes below exam) so the student can calibrate.

### Agents and the two-pass workflow
- `lecture-writer` (one per lecture, in parallel), then `bank-verifier` (one per lecture, adversarial, writes findings only), then `verify-fix-applier` (applies findings and reruns the checks). The caller integrates fragments (guide nav and sections, reference tables, tell-apart tables, glossary terms, links map, STYLE.md section, notes) by script.
- `reading-card-writer` (two to three readings per agent) and `listen-script-writer` (all scripts in one pass) for the Readings page.
- `learning-presentation-specialist` reviews the rendered site with Playwright at phone, iPad and desktop widths and writes a ranked recommendations report; it changes nothing.
- Agent definitions are in `.claude/agents/` and in `share/agents/`.

### Daily material check
- A scheduled routine fires into the working session each weekday morning: it searches the course's Drive folders for files added in the last day and reminds the student what to add (readings, deck, transcript) and what a new lecture would need before ingest. It never ingests on its own.

## How the site is checked and delivered
- `python3 build.py && node test.js && node style_check.js` after every change; `node browser_test.js` (Chromium, about five minutes) before a release; a Playwright smoke script for new pages (anchors resolve, no overflow at 390 px, no page errors).
- Delivery cycle: commit on the work branch, push, pull request, squash merge, merge main back into the work branch, republish the single HTML file as the shared artifact, confirm the GitHub Pages deployment of the merged commit.
- `CHANGELOG.md` bullets of at most 120 characters, newest first; the build embeds it.
